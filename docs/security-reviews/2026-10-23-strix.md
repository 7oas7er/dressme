## Findings

### HIGH — Mutable tag-pinned GitHub Actions in privileged workflows

- **CWE-829** (download of code without integrity check). Strix CVSS 8.9. Confidence: high.
- **Where:** all five workflow files under `.github/workflows/`.

GitHub-owned actions are pinned to **mutable tags**, while third-party actions in the
same files are correctly SHA-pinned (see commit `f57b199`). Mutable references as of
`5e11ce0`:

| Action | Tag | Files |
|---|---|---|
| `actions/checkout` | `@v7.0.1` | codeql, dependency-audit, deploy-dressme, required-ci, terraform-plan |
| `actions/setup-node` | `@v7.1.0` | dependency-audit, deploy-dressme, terraform-plan |
| `actions/cache` | `@v6.1.0` | deploy-dressme |
| `github/codeql-action/init` | `@v4.39.0` | codeql |
| `github/codeql-action/analyze` | `@v4.39.0` | codeql |

Already SHA-pinned (safe): `aws-actions/configure-aws-credentials`,
`hashicorp/setup-terraform`, `dorny/paths-filter`, `bridgecrewio/checkov-action`.

**Impact.** `deploy-dressme.yml` runs with `id-token: write` plus AWS OIDC and
`CLOUDFLARE_API_TOKEN` in scope. If an upstream tag were moved by a supply-chain
compromise, attacker code would run in that privileged job — able to assume the deploy
IAM role, overwrite S3/CloudFront content served to players, invalidate CloudFront, and
exfiltrate the Cloudflare token. In `codeql.yml` a compromised action also gains
`security-events: write`.

**Caveats / posture.** This extends the existing SHA-pinning policy from third-party to
GitHub-owned actions. GitHub itself recommends full SHA pinning for all actions, but
tag-pinning GitHub-owned `actions/*` is a commonly accepted tradeoff (GitHub maintains
those repos and applies its own controls; the deploy job only runs on pushes to
`staging`/`main`, not fork PRs, and is behind environment protection). This is a
hardening/consistency finding, not an active exploit.

**Remediation.** Replace each mutable tag with the full 40-char commit SHA for the
intended release, matching the `owner/action@<sha> # vX.Y.Z` form already used for the
third-party actions, and let Dependabot keep the SHAs current. Resolve each tag→SHA
mapping on GitHub at fix time — do not copy SHAs from the raw Strix report (its suggested
SHAs were illustrative and their version comments did not match the tags in use).

## Findings — live site (`dressme-stg.7oas7er.com`)

All three were validated against the live staging site with working PoCs. Note the
leaderboard contents were mutated during testing (see MEDIUM #2).

### MEDIUM — Unauthenticated arbitrary score submission (`POST /api/health`)

- **CWE-306** (missing authentication for critical function). CVSS 5.3.
- The endpoint requires only `x-amz-content-sha256` = SHA-256 of the body, which any
  client computes from its own payload. It is a transit-integrity check, **not**
  authentication — no token, cookie, session, or proof-of-play. Strix submitted forged
  scores (999999 / 888888 / 777777 under arbitrary 3-char names) and displaced the real
  top entries; duplicate names are allowed, so all 10 slots can be monopolised.
- Server-side validation that *is* present: score must be a positive integer (<10¹⁸),
  and names are sanitised to alphanumeric + truncated to 3 chars (so no XSS via name).
  Cloudflare rate-limits ~16 rapid requests (429) but that doesn't stop a single forged
  submission persisting.
- **This is the one real logic flaw.** The leaderboard is public and carries no money or
  identity, so impact is integrity of the leaderboard only — but it is trivially
  exploitable by anyone who reads the public `health.js`.
- **Remediation options:** short-lived signed single-use game-session token verified in
  the Lambda; and/or a server-side plausible-max-score cap; and/or per-IP submission
  throttle in the Lambda rather than only at the edge.

### MEDIUM — AWS backend details disclosed via response headers (`/api/health`)

- CVSS 5.3, info disclosure. Responses expose `x-amzn-trace-id` (X-Ray, with a
  **static** `Lineage=1:b0ddb81c:0` across requests), `x-amzn-requestid`, and — on a
  bad-signature POST — `x-amzn-errortype: InvalidSignatureException`. Maps the stack
  (S3 → CloudFront → API GW/Lambda → X-Ray). No secrets, keys, or bucket names leak, and
  the CloudFront edge node IDs in `via` 502 on direct access (no Cloudflare bypass).
- **Remediation:** strip `x-amzn-trace-id` / `x-amzn-requestid` / `x-amzn-errortype`
  (and optionally `x-amz-server-side-encryption`, `via`, `x-amz-cf-*`) via a CloudFront
  response-headers policy on the `/api/health` behaviour; or disable X-Ray trace
  propagation to unauthenticated callers at the API Gateway stage. See
  [`../security-headers.md`](../security-headers.md).

### LOW — Missing COOP/COEP/CORP; deprecated `X-XSS-Protection` present

- CVSS 3.1, defence-in-depth. The site already has a strong CSP (no `unsafe-inline`/
  `eval`), `X-Frame-Options`, `X-Content-Type-Options`, HSTS (preload), `Referrer-Policy`
  and `Permissions-Policy`. Missing: `Cross-Origin-Opener-Policy`,
  `Cross-Origin-Embedder-Policy`, `Cross-Origin-Resource-Policy`. The legacy
  `x-xss-protection: 1; mode=block` is ignored by modern browsers and should be dropped.
- Given no auth and no sensitive data, practical impact is limited to a tabnapping-style
  opener redirect (phishing, not data theft).
- **Remediation:** add COOP `same-origin`, COEP `require-corp`, CORP `same-site` and
  remove `X-XSS-Protection` via the header policy (changes go through stg apply first per
  [`../security-headers.md`](../security-headers.md)).

## Remediation plan

### Implementing now

| Item | Scope |
|---|---|
| **M1-C** | Short-lived **single-use proof-of-play ticket**: client requests a ticket at game start (`POST /api/health` with `{"op":"ticket"}`); submit must present the ticket. Lambda HMAC-signs with env `TICKET_SECRET` (Terraform `random_password`), enforces min age + TTL, and burns the ticket id in S3 (`tickets/{jti}` via `IfNoneMatch`) so it cannot be reused. GET never touches ticket material. |
| **M1-A (cap)** | Lower server `MAX_SCORE` to **500000** — reachable in a long skilled human game (line clears × level + drops), rejects the Strix-style million-class forgeries. Historical scores above the new cap remain visible on read. |

### Done (follow-ups)

| Item | Scope |
|---|---|
| **H1** | SHA-pin all workflow Actions including GitHub-owned (`owner/action@<sha> # vX.Y.Z`); Required CI runs `.github/scripts/check-github-action-pins.sh`; Dependabot `github-actions` keeps SHAs current. See [`../github-actions-pinning.md`](../github-actions-pinning.md). |
| **M2** | Strip `x-amzn-trace-id` via response-headers `remove_headers_config`; strip `x-amzn-requestid` / `x-amzn-errortype` via CloudFront Function viewer-response on `/api/health` (policy cannot remove those two — AWS deny list). See [`../security-headers.md`](../security-headers.md). |
| **L1** | Omit `X-XSS-Protection`; add `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Resource-Policy: same-origin`. COEP skipped. |

### Planned (not in this change)

| Item | Intent |
|---|---|
| **M1-B** | Lambda-side per-IP submit throttle (edge Cloudflare limit alone is not enough). |
| **M1-A (names)** | Optional best-per-name / reject duplicate-name monopoly — revisit if tickets + cap are not enough. |
| **Verify** | Re-run Strix live PoCs after stg deploy; finish white-box gaps when budget allows. |

### Explicit non-goals

- Cognito / session auth for the leaderboard (out of proportion for a vanity table).
- COEP `require-corp`.
